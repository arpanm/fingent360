# Feedback API and private attachment storage

FEEDBACK-001 uses a separate anonymous capability-owned report, not an account or financial record. Submission requires an explicit consent flag and either written text or a voice attachment. Context contains only the selected screen, runtime/version, viewport and capture date; no logs, account fields, credentials or device identifiers are collected automatically by this API.

POST `/api/v1/feedback` accepts `FeedbackSubmissionSchema` with a client-generated UUID and random 256-bit lowercase-hex receipt token. The token is stored only as SHA256; the canonical validated payload is immutable and hashed for idempotency. Retrying identical content and token returns201 with the same receipt (or its current review status). Changed content or a different token for an existing ID returns409. Deleted/expired IDs cannot be reused and return410 to the owning token. Network retries must retain the original ID/token/content. No automatic external message is sent.

GET and DELETE `/api/v1/feedback/:id` require `X-Feedback-Token`. Unknown read IDs and wrong/missing tokens return404. Deleting a never-received ID with a valid capability creates a minimal cancellation tombstone under the same advisory lock as submission. This prevents an in-flight or lost-acknowledgment POST from resurrecting a report after local deletion. New cancellation tombstones consume the same new-report quota; repeated deletion does not. Reads return the private report and attachment data, never a public attachment URL. Deletion returns200 `{id,deleted:true}` and repeated authorized deletion is harmless. Tokens are never returned or put in URLs. Clients keep them privately with the report and must not log them. All responses inherit `Cache-Control: no-store`.

POST/DELETE origins must exactly match configured `WEB_ORIGIN` or `https://appassets.androidplatform.net`. Native-origin CORS is allowed only for `/api/v1/feedback`; it does not grant cross-origin access to account or operations endpoints. There is no wildcard CORS. A JSON limit of8,500,000 bytes applies only to feedback; other API routes retain their previous parser limits.

PNG input is capped at2MB and4096×4096. Validation checks the PNG signature, chunk lengths/CRC, IHDR dimensions, supported 8-bit RGB/RGBA non-interlaced format, compressed-data expansion length and per-row filter bytes, and a complete IEND. SVG and unsupported screenshot encodings are rejected. The UI should encode a canvas/native PNG, not silently send the original arbitrary image file. Voice is capped at4MB and a declared120seconds. WebM must have EBML/WebM/segment and Opus identifiers, MP4 must contain bounded ftyp/moov/audio-handler/mdat boxes, and OGG must have bounded page framing and an Opus header. MIME spoofing/truncated framing is rejected. The server does not transcribe or fully decode audio, so duration is a client-recording bound, not a decoder-measured server duration. Playback must use the returned declared audio MIME, never execute attachment bytes.

Migration016 stores metadata and bounded bytea attachments atomically in PostgreSQL. New submissions have durable hourly address-bucket limit20 and global limit200. The address bucket is an HMAC; raw peer addresses are not stored and caller-controlled forwarded headers are ignored. Identical retries do not consume new-report quota. Limits are defensive submission controls, not a guarantee against distributed abuse.

Report content/attachments expire after30days. Feedback API activity scrubs expired content before opening its operation transaction, so a410 read cannot roll back the scrub. There is no closed-app or external scheduler claim: physical cleanup occurs on the next feedback API operation. Minimal ID/token/payload hashes and deletion timestamps remain as tombstones to prevent resurrection/replayed outboxes. Explicit deletion scrubs content/bytes immediately. This store is separate from account deletion because feedback is capability-owned and may be anonymous; users delete it through feedback history. Database backups have their own operator retention policy.

Protected operations:

- GET `/api/v1/ops/feedback?status=received&cursor=...`: up to50 receipt/context/text summaries, attachment-presence flags, no attachment bytes or receipt tokens. Stable date/ID cursor is bound to the status filter.
- GET `/api/v1/ops/feedback/:id`: private full report for an authenticated operator.
- PATCH `/api/v1/ops/feedback/:id`: `{expectedVersion,status}` where status is received/reviewing/resolved. Stale versions return409; successful review creates a new receipt version without changing the submitted payload.
- DELETE `/api/v1/ops/feedback/:id`: scrub the report with an operator audit record.

Operator reads require the existing HttpOnly operations session; mutations also require the existing configured web origin. Review/deletion audits store an opaque session-hash actor, action and version, never the token or report body.

Validation coverage: API190 covers private ownership/idempotency/retries/deletion/tombstones; API191 covers an actual PNG upload larger than the default parser bound, native-origin preflight, origin isolation and malformed attachments; API192 covers operations/private attachments/stale review/deletion; API193 expires only its own synthetic report and verifies physical content scrubbing plus replay rejection. Unit tests cover PNG CRC/dimensions/decompression/filter checks, consent/schema and malformed audio framing. Executed migration, test and final-gate evidence is recorded in [status](status.md).
