# Durable feedback delivery — FEEDBACK-001

Feedback is independent of account and financial storage. A submitted report contains only the strict feedback payload the user reviewed and consented to. The queue never reads workspaces, accounts, holdings or goals. Screenshots/audio remain attached to the submitted immutable payload until deletion; the UI must warn that a capture can itself contain visible private information.

Web reports use the separate `fingent360-feedback` IndexedDB database. Android uses an app-private native store shared across offline/CDN WebViews, with compare-and-swap revision writes. CAS conflicts retry from a fresh snapshot; storage errors never replace the queue with empty state. Each store rejects more than 100 reports or 32 MiB serialized state, preserving previous records. Native availability failures do not silently fall back to an origin-specific queue.

Offline defaults to delivery disabled and no destination. Web defaults to the configured API origin or the current web origin. Remote destinations require HTTPS with no credentials/path/query; HTTP loopback is accepted only in non-native local testing. The UI exposes delivery settings before sending. Delivery starts only for reports explicitly submitted by the user. A report binds to the first eligible destination when claimed; changing settings never moves existing or uncertain reports to another server. Restore the original destination to retry such a report.

A 60-second persisted lease protects each claimed report across tabs/process restarts. Web requests time out after 20 seconds; the same UUID and 64-hex receipt capability are reused. API creation is idempotent; receipt validation checks the returned report ID. Network errors, 408/429 and server errors retry with capped exponential backoff from 15 seconds to one hour. Other failures wait for explicit Retry. Disabled delivery and hidden-app state pause new automatic claims. Visible/open/online/native-resume events resume checking. An already in-flight request can finish after delivery is disabled; it is never represented as cancelled.

A report never attempted can be deleted locally. Attempted/sent/uncertain reports retain a deletion intent, destination and capability until the original server acknowledges DELETE. Deleting during POST retains its lease; after the POST resolves or the lease expires, DELETE proceeds. The server's capability-bound tombstone prevents a late POST from resurrecting deleted content. Failed permanent deletions remain visible for manual retry. Local report removal is not claimed while server deletion is uncertain.

Exports: `listFeedback`, `queueFeedback`, `deleteFeedback`, `retryFeedback`, `getFeedbackSettings`, `saveFeedbackSettings` from `feedback-store`; `syncFeedback({force?})`, `startFeedbackSync` from `feedback-sync`. Queue changes emit `f360-feedback-changed`. Entry `nextAttemptAt`/lease times use epoch milliseconds; `createdAt` and submission context dates use ISO timestamps. `force` is for deliberate manual retries, not background loops.

Executed verification is recorded in [status](status.md). Required acceptance covers offline submit/reload, retained attachment previews, settings pause, idempotent replay after uncertain responses, two-tab leasing, original-destination binding, account/runtime changes not clearing feedback, and tombstone deletion after an uncertain POST. Network-failure fixtures must be explicitly labelled simulations; successful submission claims require real API receipts.

Browser acceptance WEB190–193 uses actual HTML canvas screenshots, crop keyboard controls and pointer covers, and actual server acknowledgment/deletion. The voice case is explicitly `@simulated`: Chromium supplies a synthetic audio test device, while MediaRecorder, playback, attachment persistence and the feedback API remain real. A separate simulated permission-denial case checks the text fallback without submitting. Only screenshot and voice cases create reports (two per project); cleanup uses capabilities scoped to each test's unique text, never other reports. Choice/Escape/browser Back, retake preservation and draft discard cases create no server reports.

WEB194 adds an explicitly simulated lost-acknowledgment fault: the browser interceptor forwards the actual POST to the real API, retains its real receipt, then aborts only the response. Delivery is initially disabled, then enabled; the test reloads the durable queue and manually retries, requiring the original ID and receipt timestamp. Rechecking a received report must not POST again. WEB195 creates one actual report, reviews it in the operator inbox, then checks that its private user receipt becomes Being reviewed with an increased version. Each case creates at most one report per project and cleans up only its unique fixture capability. Execution evidence is recorded separately from case definitions in status.

Concurrent deletion now supersedes every in-flight POST result, including terminal errors: the next action is the capability-bound DELETE, not a permanently stalled deletion. Receipt checks apply only nondecreasing versions, so a delayed response in another tab cannot revert a newer review state. Cross-tab updates broadcast only the string `changed`; no report content, identifier or capability crosses the channel. Browsers without BroadcastChannel use a random localStorage invalidation signal; restricted native views still receive local events and reread the native store on open/resume. Incoming signals are never rebroadcast.

Authored regressions OFFLINE233–235 cover concurrent-delete terminal failure and reversed receipt ordering with explicitly simulated HTTP fixtures, plus real shared IndexedDB visibility and payload-free cross-tab invalidation. They are not evidence of a real server delivery run; parent verification records executed results.

Queue admission reserves 256 KiB below the 32 MiB hard storage limit for later leases, receipts and deletion metadata. A full queue rejects only the new submission with an actionable message; existing records remain intact and can finish delivery/deletion. OFFLINE233–235 require rebuilding the offline app assets after these client changes before execution.
