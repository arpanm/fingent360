Envelope encryption protects against disclosure of database payload copies without application keys. It does not hide owner IDs, record counts/timestamps, coarse target kind, fingerprints, due times or issued public references. These fields support authorization, joins, idempotency, paging and worker admission; their retention and access restrictions still matter. It does not replace HTTPS, device storage controls, process isolation or backup protection.

Key ring values stay server-side in ignored configuration. All active writes select PRIVATE_DATA_ACTIVE_KEY; old identifiers remain readable only while their keys stay in PRIVATE_DATA_KEYS. A read may rewrap that record and erase its legacy plaintext; reading the latest head does not upgrade every historical revision, inactive account or issued export. Parent-owned `pnpm privacy:keys`, `pnpm privacy:keys --status` and `pnpm privacy:keys --rotate` prepares the local ring; rotation must retain prior keys. Unknown keys, wrong authenticated context or invalid payloads fail closed. No plaintext fallback is allowed for a row that already has an envelope. Removing keys before a complete inventory/rewrap can make data unavailable; existing key-independent deletion/recovery remains possible. Backups may still contain earlier plaintext and old ciphertext, so encryption rollout needs a separately verified backup retention decision and tested recovery process. No automatic key retirement is implemented or claimed.

Manual acceptance: run the documented user-owned key setup, migrations, service restart and selected `pnpm sdlc` cases. Record database migration IDs, selected test IDs/projects, run timestamp and redacted failures. No test/check/format/build/migration/service/commit was run by this implementation agent. Existing working tree includes other team changes; HEAD at last inspection was a2c53a0. Validation and gated local commit remain user-owned; no push.

Update 2026-09-15: migration080 and JourneyStore now encrypt every new virtual workspace/preview/mutation/import/review financial payload. Admitted reads rewrap legacy rows. Workspace deletion verifies the capability hash directly and works without keys. API1411 is authored, not executed. This supersedes the earlier anonymous financial payload implementation gap; historical backfill and physical device/deployment acceptance remain separately unverified.

Identity rollout: root key tool creates PRIVATE_IDENTITY_LOOKUP_KEY on initial setup; an existing payload-only ring uses the explicit documented --add-identity-key first-rollout option. Subsequent rotation retains the lookup key. Missing identity keys fail closed for private identity access. Authenticated account deletion still removes owned data with session plus password without decrypting username; recovery lookup needs the stable lookup key but not payload decryption. Named operator usernames remain restricted administrative identity/audit fields; encryption does not remove their audit purpose.

Closure boundary: supported server private payload encryption, identity lookup, TOTP, support-access audit, consent and deletion/export controls are authored across their consumers. Existing isolated workbook workers enforce bounded parsing and reject formulas/external relationships; supported source/LLM adapters expose no tool authority to provider text. DEV028 now authors an encrypted Kite token vault for its gated connector; other file-only broker importers accept no credentials. Manual migration/backfill and selected-case validation are the next action, not another claimed implementation. Device-only storage remains explicitly app/browser-sandbox scoped without a newly claimed hardware vault.
