# Local server key setup

Authored, not executed. `pnpm privacy:keys` creates a server-only AES-256 key ring in the existing ignored `.env`. Existing valid keys are preserved. `pnpm privacy:keys --status` reports only the active identifier and retained-key count; `pnpm privacy:keys --rotate` adds a new active key while preserving every previous key. Restart the API to load a changed key ring. First setup also creates `PRIVATE_IDENTITY_LOOKUP_KEY`, a separate stable username lookup secret. Payload rotation preserves it.

Run these manually from the repository root. Bootstrap must already have created `.env`; no package, database connection or provider account is needed for the command. It rejects malformed, duplicate or multiline key assignments rather than guessing replacements, and rejects linked configuration files. Writes use a same-directory temporary file with mode0600, a command lock and a final comparison that refuses detected concurrent changes. Other environment entries are preserved. Avoid running other configuration writers concurrently. A stale lock after a killed process is `.env.privacy-key.lock`; inspect whether another invocation is active before manually removing it.

No key is printed or copied into browser variables, Android assets or task files. Securely back up the server key ring separately from the database. Keep old keys while any retained row, historical revision or required backup still uses them. Rotation changes future writes and the existing admitted-read rewrap behavior; this command does not scan or rewrite database rows and does not retire keys. The supported ring has at most ten keys and refuses further rotation without explicit operator retirement. Losing the only decrypting key makes its encrypted data unreadable; account recovery does not reconstruct encryption keys.

Connected feedback, private finance and MFA now depend on this configuration. Device-only storage uses its separate local policy and never receives server keys. This is an operator command, so no additional end-user form or API endpoint is appropriate. Existing encrypted-record API/browser cases exercise the application side; `tests/unit/privacy-keys.test.mjs` authors first setup, preservation, rotation, malformed-input refusal, permissions, safe status and linked/locked-file regressions.

Manual sequence: `pnpm privacy:keys`, `pnpm db:migrate`, restart `pnpm dev`, then select affected DEV-017 cases through `pnpm sdlc "Complete private server storage" -- --grep '@DEV-017'`. This broad privacy selection is deliberate; a smaller failure rerun should retain the failed case's ID and project. Check Privacy and the affected finance/feedback views at the web URL printed by dev. For failure reports, include command/stage, case ID/project and redacted diagnostics only. Agents have not run setup, migrations, checks or tests and have made no new commit.

For an existing payload key ring created before identity encryption, `--status` may report that the lookup key is missing. `pnpm privacy:keys --add-identity-key` initializes that separate key once, before migration081/identity rollout, while preserving payload keys. Use this option only for first identity-encryption setup. If encrypted identities already existed, restore their original lookup key from the secret backup instead. Normal setup/status never silently replaces a missing lookup key, and rotation refuses it. This command cannot determine whether the database has already used a now-missing key. The lookup key has no automatic rotation/retirement; changing it requires a planned complete blind-index rebuild and coordinated authentication cutover.
