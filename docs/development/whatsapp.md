# WhatsApp public summaries

Implementation authored; no provider activation or test execution is claimed.

The connected web and Android/iOS shared UI expose More → WhatsApp (`#whatsapp`). An authenticated owner consents, enters a country-code number using digits only and opens an explicit `wa.me` verification link. The user sends its single-use 15-minute challenge to the configured business number. A signed incoming webhook from that number verifies possession. Merely opening the link never verifies a number or sends a summary.

Only an owner-selected, currently published source explicitly admitted for WhatsApp redistribution can enter the encrypted outbox. The source title, summary, immutable version/hash and public reading URL are retained. The worker re-admits that exact publication immediately before dispatch; changed, withdrawn or unavailable evidence is not sent. No portfolio, goal, feedback or credentials enter messages. Ten delivery requests per rolling day and ten new verification requests per rolling day, spaced one minute apart, bound owner cost. Replaying an identical pending verification or delivery request does not create duplicates.

The approved template must have exactly three text body parameters: reviewed title, reviewed summary and public reading URL. The provider ID is retained for signed status correlation. Accepted is not delivered; delivered/read cannot regress because of late status notifications. Confirmed provider rejection permits explicit retry up to three total dispatch attempts for that request. Network failure, provider 5xx, malformed acknowledgment or interrupted dispatch remains uncertain with no automatic resend. A timeout after external acceptance cannot be made exactly once by this application; it does not pretend otherwise.

`WHATSAPP_ENABLED` controls admission; `WHATSAPP_AUTOMATIC_DISPATCH` separately controls the 30-second outbox worker. Both default false. Configure the validated fields documented in `.env.example` only after the actual business account, approved template, Graph version, permitted source IDs, HTTPS public origin and redistribution approval reference are available. No external sends were made while authoring. Source allowlisting is an operator rights decision, not evidence of permission by itself.

The webhook is `/api/v1/whatsapp/webhook`: GET performs configured challenge verification; POST requires an exact raw-body HMAC SHA256 signature and configured phone-number ID. No phone, token or body is logged. Unknown recipients are ignored. Event hashes prevent duplicate processing and cascade with the owner. Inbound STOP or in-app Disconnect disables consent and cancels unsent queued requests. Dispatch and consent/account deletion serialize through the account row. Already sent messages cannot be recalled.

Phone/challenge and message payload use the existing versioned private-data envelope. Keep every historical private-data key until these rows have been rewrapped or removed; this channel does not yet automatically rotate historical payloads. The stable identity lookup key must not rotate with payload keys. Owner privacy export includes recipient and requested public messages but excludes verification codes/provider secrets. Account deletion cascades connection, outbox, deduplication hashes and verification attempts. Disconnect retains encrypted delivery history for the owner; full deletion uses account deletion.

Offline APKs refuse verification and API delivery with an explicit connected-service message and do not queue personal numbers locally. Existing manual sharing of public links remains available. Recurring scheduling is now authored separately below; explicit requests and recurring schedules have distinct consent and quota.

## Recurring public summaries (migration102)

The same connected page now offers a separately consented daily/weekly schedule: local delivery time, IANA timezone, weekday, one to three summary messages, one to168-hour maximum age and selected operator-admitted public sources. This completes authored recurring delivery rather than leaving it as a future subscription. It never schedules private reports. One owner has one schedule, including deleted history; edits create encrypted versions and exact request receipts, with optimistic version conflicts and idempotent retries.

The existing enabled dispatch worker prepares one due occurrence before dispatch. Source selection examines at most the500 newest currently published items inside the chosen time window, intersects selected sources with the current channel allowance, skips previously scheduled item IDs and queues at most three messages per rolling24 hours. This recurring quota is separate from explicit one-off requests. Saving/resuming is capped at twenty version changes per24 hours; pause/delete remain available. Item IDs already requested by a prior non-cancelled recurring run are not repeated merely because the item was revised. A wider backlog is intentionally outside this bounded digest.

DST rules reuse the report scheduler: the first instant in a repeated local time, and the next valid minute in a spring gap (supported gaps up to three hours). Next due is visible. A occurrence over ten minutes late records `skipped` and advances to the next future schedule; it does not replay missed days. `empty`, `unavailable` and `queued` each get a durable encrypted receipt. Unique owner/version/due-time keys and owner locks prevent concurrent duplicate occurrences. There is no clock-based delivery guarantee.

Changing, pausing or deleting the schedule cancels older queued scheduled messages. STOP, disconnect and recipient replacement automatically pause future runs. Resume requires renewed explicit consent and a verified recipient. The dispatch transaction checks current active schedule version, item freshness deadline and exact source re-admission before sending. Previously accepted external messages cannot be recalled. Owner privacy export includes the actual schedule, all versions and occurrences; account deletion cascades the four new tables. Old encryption keys remain required until retained channel/schedule records are rewrapped or deleted. The shared offline route refuses schedule writes and does not claim a device background delivery capability.
