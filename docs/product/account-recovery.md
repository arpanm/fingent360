# Recovery codes — RECOVERY-001

A signed-in user may explicitly generate or rotate a 256-bit random recovery code after confirming their current password. The code is displayed once in the response and UI; only its SHA-256 hash is persisted. Users save it privately, separately from their password. Rotation invalidates the previous code immediately. No email address, verified identity or email delivery is assumed.

The displayed recovery output is a private capture region. Feedback screenshot capture places an opaque privacy cover over it; the web renderer also removes its text from the cloned document. The same pre-capture cover is used before the native capture bridge runs. Capturing or discarding a screenshot does not hide or change the owner's original recovery code, and no report is queued without submission.

Forgot password accepts username, recovery code and a new password. Incorrect, unavailable, rotated and consumed codes produce the same failure. Successful recovery atomically consumes the code, replaces the password hash and revokes all account sessions. Financial records, reading and goals remain unchanged. The user signs in again and may create a new code. Export never contains recovery codes, recovery hashes or recovery attempt identifiers.

Web API endpoints: GET `/account/recovery` returns configured/createdAt; POST `/account/recovery/code` accepts currentPassword and explicit confirmation; POST `/account/recovery/reset` accepts username/code/newPassword. All mutations require the configured Origin. Authenticated generation also revalidates its session after taking the account lock. Reset limits persist independently of password-update transactions: 30/IP and 5/normalized username per 15 minutes; generation is 5/user per 15 minutes. Expired counters are removed. High-entropy codes are compared in constant time; password hashing keeps existing scrypt concurrency bounds. Account-row locks serialize reset, rotation and deletion; consumed codes cannot be reused.

Recovery admission checks the IP budget before allocating or changing the username budget. Its PostgreSQL row lock remains held until the attempt transaction commits, so concurrent requests cannot both take the last available attempt. A full budget returns 429 immediately, keeps its counter at the cap and creates no later per-user counter. An admitted IP attempt still counts when its username budget is already full. The device handler applies the same ordering under the existing serialized storage operation. Repeated blocked requests with different usernames therefore cannot expand retained attempt state or invoke password hashing. This is a per-IP/device bound, not protection against distributed traffic from many independent addresses.

On-device accounts use the same workflow with the existing local PBKDF2 password format and private local hashed recovery state. Local mutations are serialized by the existing storage transport; failed-attempt counters must commit even when the response is an error. Recovery only applies to that device's local account, never a remote account with the same username. Recovery cannot restore an erased/uninstalled device database.

Acceptance includes generation requiring password/authentication, rotation/reuse failure, generic invalid-account errors, session revocation and correct new-password login with preserved owned data, code absence from exports, and mobile keyboard/labels/one-time display. Implementation and executed verification are tracked separately in TODO/status by the parent integration task.

Authored regression cases: API210 (rotation, generic failure, concurrent old-password login/reset, session revocation and retained watchlist), API211 (durable failure limits), API212 (29 real failed attempts, concurrent admission at the 30th IP attempt, then unchanged counter count/value for 25 blocked new usernames), WEB210 (one-time display and forgot-password UI), OFFLINE250–251 (local reset/reuse/preservation and limits across reload), OFFLINE252 (the device admission boundary, saturated counters and unchanged cardinality after blocked new usernames and reload). API212 and OFFLINE252 use unknown synthetic usernames with the actual application handlers, hashing and owned persistence; no successful recovery or production data is fabricated. Existing deletion-budget unit fixture now permits the newly required account-row lock before reaching the budget guard.
