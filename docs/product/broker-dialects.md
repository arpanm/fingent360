## Implemented fallback policy

The existing Map CSV columns flow gains an explicit choice: use a total-acquisition-cost column, or supply costs from the user's records. The original `user-mapped-holdings-csv-v1` path and three-column validation stay unchanged. The new `user-supplemented-holdings-csv-v1` accepts at least two distinct columns, selected ISIN and quantity, the same bounded CSV grammar and at most 200 data rows. No automatic column or broker inference occurs.

The supplemental input's canonical JSON is capped at 100,000 UTF-8 bytes, leaving room for account-version and storage-consent fields under the existing API body limit. This guard also runs locally. A large file must have unused columns removed from a copy while retaining the complete intended holdings list; splitting the replacement into partial imports is not suggested.

For supplemental input every source row requires a cost and a receipt binding the CSV record position (header is row 1), exact normalized ISIN and exact quantity text. Newlines inside quoted cells do not count as additional records. The user chooses INR rupees or whole paise, explicitly names the records used (trade confirmations, prior broker records or personal acquisition records), and attests that these are total acquisition costs for the stated quantities, not an estimate obtained from average prices or market values. There is no default cost, basis or attestation. Zero must be entered explicitly; blank, negative, formula, exponent and over-precision amounts reject. Changing the file, columns, unit or provenance choice clears affected costs/attestation. No average-price multiplication or rounding occurs.

Declared source row count and an independently reconciled acquisition total must match every supplied row and exact integer-paise sum. Duplicate ISINs reject unless the user explicitly combines quantities and costs. Supplemental metadata has a strict origin discriminant, records basis, attestation, mapping positions and immutable per-source-row ISIN/quantity/cost receipts. Broker average/valuation columns remain discarded and are never relabeled as acquisition costs. Raw files, column names, filenames and ignored cells are not stored. The financial snapshot remains `user-entered-unverified`.

Both API and device handlers reparse the request before the existing owned preview. Consent to storage, replacement comparison, removal acknowledgement, version conflict, expiry, exact confirmation replay, history, complete privacy export and account deletion reuse the existing holdings workflow. Editing normalized rows explicitly discards the source/supplemental provenance. Cancel restores the earlier draft; a failed preview preserves the prepared reconciliation for retry. Review, saved holdings and history disclose supplemental provenance. No new table, migration, dependency, worker, provider call or account credential is required. Offline uses the same pure parser and persisted local bridge with zero API traffic.

Acceptance requires strict row binding and totals, precision beyond binary floating-point safety, source fields unable to masquerade as user attestation, duplicate/empty/bounds behavior, ownership/origin/stale preview/replay, immutable history and privacy deletion; keyboard/mobile normal clicks, error/retry/cancel/edit and 401 clearing; durable device parity and packaged help. API/WEB/OFFLINE720–739 are reserved. Authored case IDs and exact manual actions are recorded in the handoff. Implementation and external format evidence remain separate from user-run verification; the named broker portion of DEV-008/SRC-013 remains partial.
