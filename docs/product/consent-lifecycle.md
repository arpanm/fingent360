# Purpose consent lifecycle — CONSENT-LIFECYCLE-001

DEV-017 child, implementation authored; verification remains user-run. This is an application control for four concrete uses, not legal certification or completion of the broader privacy/security parent.

Account creation/storage consent is not a grant for any purpose. External private-context sharing has no retained historical consent record, so it starts ungranted. An existing `library_preferences` row explicitly set to `for_you` can supply a labeled legacy basis; its grant date is unknown because that table does not record one. Existing immutable schedule request receipts can supply their actual schedule/version/request/date as a legacy basis. Reads never manufacture immutable grant events. Legacy basis is displayed separately from a reviewed lifecycle grant.

New explicit For-you, schedule save/resume and automatic-material-settings actions record their first purpose opt-in atomically with that actual action when no lifecycle head exists. Once an explicit head is revoked or expired, repeating preferences, schedule edits or old idempotent requests cannot regrant consent. Renewal occurs through the purpose review. Missing configuration, merely existing records or account storage consent do not create authority. Automatic material checks have no legacy grant. Their separate enabled setting binds the consent version; renewal cannot silently resume an old enabled baseline. An explicit Enable/Resume after renewal establishes a fresh baseline and next due time (MATERIAL-AUTO-001).

## Ledger and user workflow

Migration043 adds up to four owned purpose heads and immutable event receipts with an account-owner sequence index. Account deletion cascades; ordinary revoke preserves all records. Each request has a UUID, expected purpose version, fixed policy version and explicit review confirmation. Same request/body returns the original receipt; changed content under the same request ID conflicts. Grant/renew may choose no expiry or a specific future expiry within 366 days. Expiry is a wall-clock derived state; reads do not silently write events. Known future grant/change/basis timestamps are unavailable and cannot authorize use; actual unknown-date legacy reading remains explicitly labeled. Renewal records a new grant/version, and revocation records a new denial/version. Source text, model output and unrelated saves cannot perform these actions.

Privacy → Purpose consent exposes each purpose, controlled data/use, current or legacy basis, expiry, grant/renew/revoke review, saved receipt and immutable paginated history. Current state is fetched separately from replay receipts; a failed follow-up read retains the receipt while marking current context unavailable. Loading/empty/error/retry/cancel/conflict states preserve a user's draft and require fresh review after a version conflict. Typed401 clears protected controls and old asynchronous results cannot restore them. Account links and the affected workflows expose Privacy recovery links.

Complete privacy download follows all bounded consent-history pages under a fixed owner/upper sequence, together with the existing complete schedule/reading/material exports. No silent truncation or partial successful download is allowed. The standalone purpose history also supports bounded pages; there is no lifetime event cap. Raw user questions/provider replies are not stored in consent receipts.

## Admission, expiry and revocation

All owned operations use account-first locking and current-clock authentication after waits. Purpose changes take account UPDATE; consuming reads/captures take account SHARE or the schedule worker's existing account UPDATE. The grant is rechecked after any later storage/source wait and before protected use or commit. A read admitted before revocation may complete under its held lock; a use admitted after committed revocation is denied or uses the defined chronological/query fallback.

Remote dispatch uses a short admission transaction: account SHARE, session reauthorization, current source admission, exact active grant version/expiry, then synchronous start of the fixed-provider request. The network promise is awaited after releasing database locks. A request admitted before revocation may already have been sent; revocation cannot recall it. The final result transaction checks account/source admission and the same grant version/expiry. Changed, expired or revoked authority discards the provider result, including a revoke followed by renewal, and returns only ordinary query-based matches. Provider output never renews a grant. No credential or private content enters the ledger.

Private candidates also bind their actual goal id/version, holdings version or saved-reading item/version. Both the dispatch and final response transactions revalidate existence/version under account admission. An edited or deleted record cannot send an old candidate after the change commits, and an old provider reply cannot return that private text after a later record change. Internal bindings are absent from provider inputs and public source contracts. Ordinary query fallback is filtered through the same final current-record check.

Reading ranking uses chronological order while its grant is absent/revoked/expired, with an explicit reason. Stored preferences remain intact. Consent version/effective state participates in page identity; a page cannot continue a personalized order across a purpose change without reset.

Scheduled workers retain worker-control admission first and canonical account-before-schedule locking. They exclude denied/expired purpose heads before selecting work, then recheck before a snapshot is stored and after waits; denial rolls back the entire capture without a hidden report or capacity increment. Existing already captured report jobs can finish. Revocation does not delete or rewrite issued reports. Renewal after a lapse moves active schedules to their next future occurrence under the same account lock and records those bounded scheduling effects in the consent receipt. There is no surprise catch-up for time when consent was absent. Paused schedules remain paused; resume still uses the existing next-future rule.

## Device behavior and acceptance

The device bridge uses the same schemas/reducer, exact expiry policy, immutable receipts, current-versus-replay distinction and complete export. Its serialized storage prevents overlapping writes. Local assistance never dispatches AI; grants do not enable a network capability. Personalization and device-open schedule captures honor their purpose state. Deletion removes all owned consent data. No background server behavior is promised while the device is closed.

Authored API760–768 (9), WEB760–764 (5, each desktop/mobile) and OFFLINE760–762 (3), plus five contract units. Cases cover explicit/legacy absence, grant/renew/revoke/expiry, exact replay/conflict, foreign ownership, post-wait session and consent expiry, remote dispatch/result timing with a clearly labeled synthetic transport and real owned storage, private-record edit/removal, unchanged financial records, schedule admission/no catch-up/pause, complete multi-page export/deletion, privacy401 clearing, keyboard/mobile review and zero device API traffic.
