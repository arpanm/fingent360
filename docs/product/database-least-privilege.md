# Separate PostgreSQL runtime and migration credentials

DB-LEAST-PRIVILEGE-001 separates the credentials used for application queries from the credentials used to own and migrate its schema. Existing installations remain compatible: without `MIGRATION_DATABASE_URL`, the migration command uses `DATABASE_URL`. That fallback does not enable least privilege. Enabling the separation is an explicit local administrator action, never application startup behavior.

`DATABASE_URL` remains the runtime connection. `MIGRATION_DATABASE_URL` names the same database/schema using its existing owner. The application configuration does not expose the migration URL to stores. The development launcher and production start wrapper remove the migration setting before starting the API. The port allocator preserves both users, passwords, database names and options while updating their local ports together. No real `.env` file is edited by this feature's author or provisioner.

## Manual workflow and recovery

After the user builds the API and applies existing migrations with owner credentials, they privately configure both URLs. `pnpm db:roles` reads and validates a preview; `pnpm db:roles --apply` explicitly creates a distinct marked runtime role and grants access atomically. Both commands require loopback connections to the same existing database/schema. They print only a fixed result and safe role/schema identifiers, never connection strings, passwords, password verifiers or raw driver errors. Missing or unsafe configuration explains the required administrator action.

The new role has LOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOINHERIT, NOREPLICATION and NOBYPASSRLS. It owns no database, schema, table or function and receives no role memberships. It receives only schema USAGE, table SELECT/INSERT/UPDATE/DELETE and sequence USAGE. The migration ledger is read-only for runtime. Immutable triggers remain effective; TRUNCATE, trigger changes, persistent DDL, SET ROLE to the owner and database/role management remain denied. Existing PUBLIC temporary-table rights are not widened or silently revoked; persistent application-object authority is the boundary of this child.

The provisioner refuses PUBLIC/effective CREATE on application or other ordinary schemas, unexpected role attributes/memberships/ownership, objects owned by someone other than the migration owner, and existing roles without its exact database/schema/owner marker. It does not take over, rename, rotate credentials for or alter unrelated roles. An administrator must resolve unsafe pre-existing grants explicitly. Remote/custom administration is documented for manual review and is not silently modified by the local helper.

The owner installs schema-scoped default privileges for future tables and sequences. The migration command refreshes those grants after applying migrations when separate credentials are configured, within the migration transaction; its ledger keeps only runtime SELECT. A runtime URL accidentally used as migration owner fails before schema changes. Repeating provisioning returns the same effective plan and does not change passwords or stored data. All provisioning statements roll back together on failure. Existing live sessions should be restarted with the new runtime URL after success; rollback of configuration is an explicit user choice, never an automatic promotion of the API to owner credentials.

## Isolation, acceptance and limits

Existing E2E fixture owners use `MIGRATION_DATABASE_URL ?? DATABASE_URL` to create/migrate/drop only their random schema. The normal configured application namespace is never altered by role tests. A dedicated fixture creates a unique marked runtime role for its owned schema, drives the actual application with that role, then closes the API and owner-drops only that schema/role. No setup runs during test discovery.

API580–589 are reserved for actual runtime registration/goals/holdings/readiness, table DML and sequence allocation, denied persistent DDL/role escalation/TRUNCATE, owner migrations and default grants, immutable-history preservation, repeat/rollback/refusal and fixture ownership checks. Unit cases cover safe URL/identifier validation, migration-target selection and port preservation. All test records and credentials are explicitly synthetic and never attached to traces or logs. Execution is user-only; authored assertions are not verification.

UI/UX/mobile/offline: no new end-user control or private dataset. Existing responsive account/holdings workflows and readiness responses are reused; operational storage errors explain the owner/runtime configuration remedy without revealing credentials. Device-only storage and MongoDB permissions are unchanged. This does not implement production secret distribution, encryption, broker-token storage, database row-level tenancy or named operator roles. No provider call, schema migration, service, dependency or scheduled job is introduced by authoring this child.
