# DOMAIN-CONTRACTS-002 — reusable educational domain contracts

This child implements the missing DEV-003 reusable schema categories and golden fixtures. It is authored in the main working tree and awaits user validation; it is not a new deployed database model or event/policy workflow. Earlier features supplied contracts and persistence for their own screens, but did not supply reusable event/edge, acquisition-lot, financial-profile or educational policy-result records. DEV-006/010/019 remain separate consumers. Synthetic fixtures are never imported by the app.

Versioned records use opaque UUID identity, positive version, creation time and an explicit prior-version/reason pair (null for first revision). Evidence binds exact document identity/version/hash and a bounded locator; a graph checks every referenced edition and claim. Facts, expectations, scenarios and inferences retain distinct tags. Review/publication and freshness do not prove truth. A bounded directed acyclic graph validates typed endpoints and evidence references, not causal correctness; no numerical sensitivity is inferred.

Lots reuse AccountHoldingSchema quantity/cost/ISIN and quantityMillionths. INR scale2 remains the sole money convention. Owned portfolio snapshots reject foreign lots, duplicate lot IDs, missing/orphan holdings and exact quantity/cost reconciliation mismatches. Totals sum integer paise; no prices, FX, return, corporate-action or tax calculation. Acquisition dates are valid calendar dates or explicitly unknown. A known acquisition cannot follow its lot capture, and a lot revision cannot follow the portfolio snapshot that contains it.

Profile inputs are explicit user-provided/unknown financial and risk-context fields, not suitability conclusions. Policy result is educational only with no action; it binds actual supplied portfolio/profile/goals/evidence revisions, records policy/evaluation/freshness and requires an unable-to-assess result when inputs are stale, unknown or conflicting. The pack checks the actual supplied inputs: unknown profile fields, unreviewed/withdrawn referenced claims and contradicting evidence cannot be hidden by declaring freshness current. Referenced goals retain the existing exact contribution-only projection, and every evidence link resolves in both directions. All evidence attached to a selected claim must have existed at evaluation, including contradictions omitted from the result's evidence selection. UTC ordering preserves submillisecond precision. A literal unchanged-record comparator is mandatory. Validation cannot establish real-world currentness, authenticate an owner, authorize a trade or generate a recommendation.

Records reject unknown fields and bound collection sizes and financial precision. Thirteen golden groups cover all seven DEV-003 categories: reusable ISIN/observation primitives; complete event → factor → sector → instrument reconstruction; broken evidence/hash/version references and multi-edge cycles; exact lot sums beyond binary-float precision; mixed currencies/owners, duplicate/missing lots and capture dates; multiple goals of the same type; current, revised and unavailable result packs; input immutability; stale/conflicting policy refusal; and unknown extra fields. These are deterministic synthetic fixtures, not provider samples or proof of real-world inference.

The domain types and invariants are implemented as source code; validation is pending. The database changes for earlier working features already exist, but this child adds no tables, migration, API, UI or worker. No dependencies change. A schema parse validates a supplied snapshot and its internal consistency; it cannot prove prior versions exist in storage, enforce immutability after callers modify an object, verify an owner or guarantee freshness. Referenced originals and source rights still require admission by the eventual consumer. Declared evidence hashes are compared, not recomputed without document bytes. Runtime/public readiness must not be inferred from these schemas.

Manual acceptance is the category and fixture review in [the handoff](../development/domain-contracts-handoff.md). User-run checks must precede any new verification or commit claim.
