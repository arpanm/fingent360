# Contribution-only goal comparisons — GOAL-SCENARIOS-001

A comparison captures one actual saved goal edition and one to three alternatives entered by its owner. Each alternative changes only monthly contribution and horizon (1–1200 months), leaving saved amount, target, goal type/name and the explicit no-growth assumption unchanged. There are no suggested personal amounts, returns, market values or recommendations. Calculations use integer paise: saved + monthly × months; remaining gap is max(target − projected,0). Signed differences compare each result to the unchanged plan. This is a contribution record, not a forecast including inflation or investment growth.

Lifecycle: Goals → Compare plans → choose saved goal → enter alternatives in rupees/months → review unchanged plan alongside alternatives → consent/save immutable comparison → reopen/history → select alternative → review exact edits → explicitly adopt. Saving never edits a goal. Adoption checks the owned goal still matches the captured baseline revision, inserts a normal goal edition, and records an immutable idempotent adoption receipt. Existing allocation plans consequently require review through normal version checks. A stale or deleted baseline cannot be adopted; create a fresh comparison. Prior comparison/adoption receipts remain historical. Repeat requests return the same receipt, never claim it is the current goal after later edits.

The UI preserves a failed save's draft and request identity. Failed current-state refresh leaves historical receipts clearly labelled and adoption disabled until reload. Account deletion cascades all receipts; exports include owned comparisons/adoptions. On-device behavior uses the same exact contracts and local transactional storage without network or automatic synchronization. Cap at 100 comparisons per account; up to 3 alternatives each. No automatic deletion/revision rewriting.

An initial unavailable or unreadable comparison response shows an explicit Retry comparisons action even before any data has loaded. Saving or replaying a comparison immediately marks current goal context unavailable, retains the validated historical comparison, and requests current goals again. If that refresh fails, the saved receipt stays visible, adoption remains disabled and Retry comparisons is available. A successful retry evaluates the current goal edition; a changed baseline still requires a new comparison. A stored comparison receipt is never evidence that its goal edition remains current.

Acceptance: exact16-digit inputs and long horizons; baseline reconstruction; saving without financial mutations; stale/deleted/foreign targets; parallel adoption and request replay; immutable export; allocation review after adoption; manual desktop/mobile keyboard/back/dirty-draft handling; offline restart and privacy/deletion. Authorship does not imply executed verification. Wider suitability, tax, return forecasting and regulated advice remain outside this child.

WEB283 commits a real comparison while losing its response, changes the actual goal, retries the identical request, then fails the context refresh: the historical comparison remains visible with adoption disabled. Restoring GET and retrying shows the changed-goal warning and leaves adoption disabled for the old baseline.
