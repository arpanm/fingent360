# Guided CSV mapping — MAPPED-IMPORT-001

This authors a complete user-defined import workflow under DEV-008/SRC-013. The chosen initial broker research order is Zerodha, Groww, Upstox, Angel One and ICICI Direct, following the user's authorization to choose and research formats. Public documentation and browser-visible examples were inspected on 14 September 2026. The findings below appear in My holdings → Broker export help and supported imports. Named automatic adapters remain unimplemented because the researched material does not establish complete versioned file layouts and acquisition-cost reconciliation rules. Mapping is useful now without labeling a user-defined file as a verified broker export. Validation remains for the user's manual run.

My holdings → Map CSV columns accepts a UTF-8 comma-separated file with one header row, at most 32 distinct nonempty headers, 200 data rows and 50,000 characters (browser upload also caps bytes at 50 KB). Standard CSV/XLSX and manual entry remain available. Values are parsed as strings; quoted fields and escaped quotes work, while malformed quoting, unequal row lengths, blank data rows and control characters reject. No formula execution, provider calls, filename/header/raw-file persistence or automatic broker inference occurs.

The user explicitly selects three distinct columns for Indian ISIN, quantity and total acquisition cost; chooses whole INR paise or INR rupees (two decimal places); and enters the source row count and source acquisition-cost total in that chosen unit. No default columns or monetary units are inferred. Average purchase prices, market values, returns, transactions, shorts and unsupported assets are not converted into holdings. Ignored columns are discarded and their count is disclosed. The user must verify that the file represents the complete holdings replacement.

Duplicate ISINs reject by default. An explicit combine choice sums quantities in millionths and costs in integer paise, without rounding, and reports source versus consolidated row counts. Aggregates must fit the existing holdings limits. The declared source row count and total must match exactly before a normalized draft or server preview is accepted. Invalid input leaves existing saved holdings and the prior prepared draft unchanged.

Review first prepares a local normalized draft; explicit storage consent and the existing owned preview then reparse the original CSV text and mapping on the server (or device adapter). The existing replacement comparison, removal acknowledgement, version conflict, 30-minute preview, idempotent confirmation and immutable revision history remain authoritative. Editing normalized rows explicitly discards mapping provenance and returns to standard CSV. Corrections to mapping invalidate the prior prepared draft and preview. Cancel returns to the prior holdings draft; leaving warns about unsaved mapping input. Pending controls are disabled; late file reads and 401 cannot restore private imported content. A failed preview preserves the reconciled draft for explicit retry.

Only normalized holdings and bounded metadata persist: parserVersion `user-mapped-holdings-csv-v1`, column positions, selected cost unit/duplicate policy, input column count, declared source row count/total and consolidated count. Provenance remains user-entered-unverified. Existing JSON preview/revision records support this additively without a migration, and existing privacy export/account deletion carry/remove the metadata. On-device mode uses the same parser and durable workflow with zero API traffic. A rebuild is required for packaged device changes.

Acceptance: exact quoted/long-number conversion; intentional duplicate consolidation; declared-count/total rejection; malformed/ambiguous/formula numeric input rejection; failed import preserves saved records and prior draft; keyboard/mobile mapping/review/cancel/correction; actual connected ownership/origin/sign-out and replay; stale baseline and mandatory removal-consent recovery; metadata-only history/export and deletion; offline persistence and bundled broker help without API traffic. API610–613, WEB610–615, OFFLINE610–611 and five contract unit cases are authored. WEB613 delays actual selected-file bytes; WEB614 simulates only a 503 failure and retries against the actual isolated API. WEB610 captures a deliberate synthetic review image; automatic private traces/video/screenshots are disabled. The user performs validation.

## Layer coverage

Contracts and domain: bounded strict input and retained metadata schemas, exact paise/millionth arithmetic, five goldens. API and functionality: existing authenticated preview/confirm workflow with server reparsing, source-total checks, version conflict, explicit removal and receipt replay. Data model: additive JSON metadata in existing previews/revisions, reused export/deletion; no new tables or migration. UI and UX: explicit column/unit selection, duplicate consent, source totals, loading/error/retry/cancel/review/save, private masking and keyboard/mobile cases. Real data/provenance: primary documentation links for the five research targets, synthetic fixtures clearly labeled and no verified-broker claim. Offline: same parser/local serialization, saved metadata and static help. Automation: no new worker, provider fetch or scheduled task is applicable to a user-selected bounded file. Documentation: this specification and the exact manual handoff. DEV-008/SRC-013 remain partial for the five named adapters until those specific evidence gates are resolved and implementations are authored; MAPPED-IMPORT-001 has its own complete authored scope.

All mapped request variants enforce a100,000-byte canonical UTF-8 JSON limit in addition to the CSV character/cell bounds. This leaves room for account-version/storage-consent fields under the100KiB API limit; the local handler applies the same rule.
