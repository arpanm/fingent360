# NAMED-OPERATORS-001 — explicit named administration and independent publication

This child adds an explicit `OPS_AUTH_MODE=bootstrap|named` deployment choice. Bootstrap remains the existing local shared-key behavior; setting named mode rejects shared-key sign-in and direct legacy bearer administrative routes. Merely deploying the schema does not enable the new mode. Initial named administrators are provisioned only by an explicitly user-run local owner command, with no default identity/password, printed secret or browser bootstrap endpoint.

Named sessions bind an immutable operator ID and current permission revision. Roles: viewer reads protected operational data; researcher reads, prepares/imports drafts and proposes public changes; publisher reads and independently approves/rejects proposals; admin manages named identities, operational controls and can propose or approve subject to the same distinct-identity rule. No identity may approve its own proposal even using another session or holding admin. Public-data decisions are not legal rights approval: operators record evidence; the application cannot grant source licences.

A centralized guard covers every registered Operations handler. Read handlers require explicit operational-read metadata; mutation handlers require explicit action metadata. Unknown operational handlers fail closed in named mode. Bootstrap login/logout/session introspection remain bounded explicit exceptions. Direct legacy bearer source/macro administrative paths are disabled in named mode; internally authorized source/macro adapters remain available through guarded Operations routes. Role management disables/revises identities and invalidates prior sessions; each final post-storage authorization must also validate active identity/current role revision and wall-clock expiry, not only the cookie hash.

Four-eyes proposal workflow covers discovery publish/withdraw, media publication/unpublication and source-registry rights/publication changes. Proposals contain typed target/body, examined target version/asset binding, proposer ID, immutable creation time and request identity. Propose does not change public state. A distinct publisher/admin reviews the exact proposal and actual retained target, then explicitly approves or rejects. Approval verifies current source/media/registry bindings after storage locks. Public revision and completed approval receipt commit in the same PostgreSQL transaction. A changed head conflicts without publication; a new proposal is required. Repeated approval returns the immutable historical receipt, not a fresh current-state assertion. Withdrawn original bodies remain operator-only. No automatic publication, provider call or generated licence decision.

UI: Operations sign-in selects the configured mode, shows current named identity/role, and exposes readable permission failures without suggesting local keys grant named access. Named administration adds identity creation/disable/role-revision controls with explicit confirmation; publication proposal list/detail exposes author identity, target/revision, complete proposed changes, approval eligibility, rejection reason and immutable outcome. Existing publication editors create proposals instead of changing public state in named mode. Draft/receipt/Back/loading/empty/error/conflict/401 handling retains the existing session generation barrier. Device mode stays connected-only with no API traffic until connected operation is explicitly configured.

Migration038 adds identities/session bindings/proposals/audit history additively. Historical bootstrap sessions/audit rows retain their original meaning; no actor name is inferred for old hashes. No account financial record changes. Internal authorization and immutable proposal history are operational records, not investor privacy exports. Named-user credentials never enter audit/export/public data. Provisioning, mode-switch recovery, final-admin protection and exact retention bounds must be documented before acceptance.

Acceptance uses actual isolated named identities and storage: permission matrix/direct endpoint bypass, shared-key denial in named mode and unchanged bootstrap mode, distinct-identity approval including one identity in different sessions, stale heads and exact replay, public source/media/rights state changed only by approved proposals, rejected/expired/revoked identities after waits, existing private finances/public evidence unchanged, full mobile/keyboard sign-in/propose/approve/history/Back and late-response clearing. API/WEB640–659 reserved; migration038_named_operators.sql. Authored work does not imply executed verification. User owns builds/migrations/services/tests/gates/commit; no external deployment or push by the agent.

## Final admission and recovery

Identity changes and owner recovery increment the permission version; they do not delete session rows while changing the identity. Thus an old operational transaction holding a session-row read lock cannot prevent a different administrator from committing a disable. Its later admission rejects the old version. A decisive proposal completion takes a short identity read lock after the resource/proposal locks, so a role update committed before this admission fences the mutation; an already admitted transaction completes before the later identity update. No identity lock is held across a provider request. Named identity updates serialize on one gate and never permit self-edit, including differently cased UUID paths.

There are at most50 retained operator identities and100 pending proposals. Disabling does not erase attribution; existing identities can be re-enabled, and administrator recovery can target an existing identity at capacity. Decided proposal history is immutable and paginated50 entries per request, with a validated signed-bigint continuation. No silent expiry or lifetime decision cap. Administrative change rows are retained immutably as database audit records; the current UI shows permission revisions, not a claim of a complete change-history browser.

ECB policy-rate edition publication/withdrawal also uses independent proposals. Existing direct World Bank macro and security-identity refreshes remain authorized ingestion pipelines rather than newly introduced two-identity publication workflows. This boundary does not claim every datum has two-identity review. A proposal for rates binds the exact head version and a previously unused rate-review request ID.

An identical decided approval/rejection retry by its actual deciding operator returns its saved receipt. A concurrent approval that lost the race rolls back its public writes and reports conflict; reopening or retrying reads the immutable outcome. Saved receipts explicitly do not assert the source's current public state. Source and visual editors reuse an uncertain proposal request identity for the same exact input; there is no auto-publication on retry.

## Explicit owner setup (manual only)

Keep `OPS_AUTH_MODE=bootstrap` until the user chooses named administration. After normal install/build and migration038 (and040 for the registered ECB module), privately supply the existing migration owner URL and temporary `OPERATOR_USERNAME`/`OPERATOR_PASSWORD` environment variables, then run `pnpm ops:provision`. It prints only a permission revision. Clear the temporary variables, set `OPS_AUTH_MODE=named`, and restart the API. Sign in at `/#ops`; create a distinct publisher before proposing a public change. A publisher cannot create users; a researcher cannot approve; even an administrator cannot approve their own proposal.

For deliberate password/admin recovery, use the same owner command with `--recover` and the chosen existing username. This rotates the password and permission version, invalidating old sessions without erasing proposal attribution. Merely restarting never provisions credentials. Do not put credentials in Git, test traces, browser URLs, screenshots or copied terminal output. The helper returns safe validation/recovery guidance and conceals driver details/URLs. To switch deployment modes, explicitly change configuration and restart; each mode rejects the other mode's session identity.

No deterministic checks have been run by the author. API640–644, WEB640–641 and contract/guard test definitions are authored; coverage claims remain pending user execution.

Authentication establishes distinct named identity IDs, not that two real people are different. Administrator assignment and credential handling govern that organizational trust. The server prevents one ID from reviewing its own proposal across sessions or roles.
