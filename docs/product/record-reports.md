# REPORTS-001 — saved-record reviews

A signed-in user requests a dated review of their saved goals, holdings and explicit allocation records. The request captures an immutable snapshot in one consistent transaction. A queued job prepares a deterministic educational report from that snapshot; later edits to the source records never rewrite an issued report. The report is a record review, not a market valuation, suitability check, trading instruction or personalised recommendation.

The request → queued/running → issued → open/download journey works in the web app and bundled Android app. Server jobs use PostgreSQL leases, a bounded retry policy and idempotent issuance. Offline work resumes when the report page is opened/refreshed; it does not claim an operating-system background worker. Users can cancel work before issuance. An issued report and its captured source versions stay available in owned history and privacy export until account deletion.

Each report shows captured goal names/versions and target/saved/monthly amounts, contribution-only projection and remaining gap using exact integer paise. It separately lists entered holdings and their recorded total cost. Allocations, where captured, describe assignments of recorded holdings cost and must not be added to already-entered goal savings. A visible caveat warns that the same funds may otherwise be counted twice. No growth, market price, tax, fee, inflation, withdrawal or return is inferred.

Acceptance requires strict shared contracts, saved input identity and timestamps, one issued result for every idempotent request, truthful progress/failure/retry/cancel, ownership across list/detail/download, no source mutation, lease-expiry recovery, accessible keyboard/mobile controls and offline persistence. Empty saved records yield an explicit empty review, never synthetic holdings. Privacy export includes jobs/snapshots/issued records; account deletion removes all associated rows. Execution evidence is maintained separately in development status.

## Implemented contract and operation

`POST /api/v1/account/reports` requires `{requestId, label, consent:true}`. The UUID is an idempotency key; retries preserve the original snapshot and a changed label returns 409. The account row lock makes capture coherent with goals, holdings and allocation saves. `GET /account/reports` lists up to 100 owned jobs; `GET /account/reports/:id` returns status and the immutable report. `/download` returns validated JSON after issuance. `POST /:id/cancel` and `/retry` require `expectedVersion`; cancellation is only possible before issuance and retry only after failure. Each explicit retry starts a new bounded three-attempt cycle for the same snapshot. Account deletion cascades jobs and reports; privacy export includes `{jobs}`.

The API worker polls every two seconds, acquires a 30-second lease with `FOR UPDATE SKIP LOCKED`, and retries recoverable failures after ten seconds. A failed third attempt or expired third lease becomes failed. Lease identity and expiry fence publication; cancellation invalidates the lease. Invalid persisted snapshots are validated after the claim commits, so validation failure consumes an attempt instead of rolling back forever. There are no import-time timers or external jobs/services. Shutdown stops polling and awaits the active attempt.

Offline uses the same report schemas and exact calculation policy. Jobs persist under the local account and are prepared on subsequent report reads while the app is open. A closed app does not process queued work. Both modes retain allocation revision, original cost assignments and review reasons; allocations never increase the contribution-only goal estimate. Downloads use the existing browser/Android save-file flow. The reader opens in the accessible dialog with Escape/native Back and focus restoration.
