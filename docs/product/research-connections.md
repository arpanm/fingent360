# Your research connection — EVIDENCE-LINKS-001

An investor can record why one published research edition matters to their own thinking about one saved holding or goal. This is an explicit user-authored research connection. The application does not claim exposure, price impact, sector classification, causation, suitability or advice. It does not change financial records or send them to a provider. OpenFIGI remains identity metadata only.

## Contract and workflow

Reader → Connect to my records → select an owned saved holding or goal → write a personal reason (1–1000 trimmed characters) → consent to private storage and retained history → review the exact source/target editions → save. Holdings, Goals and More link to the connections workspace. The workspace supports detail, edit note, explicit reaffirmation, removal and dated history. Removal is an immutable revision and removes the connection from the active list; history remains in private export until account deletion.

Only current published non-draft editions from the existing permitted Fed, ECB press/statistics, PIB or World Bank collections with a source hash can be bound. Source inputs include item ID, exact edition and hash. The receipt contains those values, source name and HTTPS URL, publication/retrieval dates and the provider's effective-period label. It contains no article title, summary or body, so history cannot republish withdrawn text. Reader/source links refer to the current published edition only after an authoritative context read; a saved historical receipt never establishes current publication status. A newer published edition, withdrawal or removed publication requires review. Unpublished drafts do not supersede the last public edition.

Holding identity is the exact owned ISIN plus the account's holdings snapshot version; any holdings revision conservatively requires review. Goal identity is the exact owned UUID and goal version. Target labels are user-record labels, never fuzzy security matches. Removed targets can be inspected through the saved receipt and removed connection history; they cannot be reaffirmed. Reaffirmation preserves the source and target identities, binds current exact versions, requires renewed consent and creates a new revision. Editing the note never silently rebinds versions or clears review status.

## Persistence and concurrency

Migration024 adds owned connection heads, immutable revision receipts and account-scoped request receipts. Every write locks the account row first, then the connection head, then the source item. Holding/goal writes already lock the account first. Publication writes lock source items, so source validation and save are serialized. Strict schemas reject extra fields; origin, session, target ownership, publication state, expectedVersion and request ID checks run inside the transaction. All private connection reads and writes recheck the session after the account lock, so requests admitted before a recovery reset cannot read or replay receipts or write after their session is revoked. Same request ID and identical normalized input replay the original immutable revision; different content or connection with that request ID conflicts. Removed heads remain unavailable for further edits. A maximum of 200 active connections per account bounds the workspace.

The UI immediately retains a validated successful mutation receipt or removal, then refreshes current context. A replay may return an older receipt, so it cannot supply current source/target values or clear review warnings. Until an authoritative GET succeeds, the UI labels current status unavailable, hides current-source links and source/target selection or reaffirmation, and offers Retry. The saved receipt and any existing warnings remain visible. Failed PUT requests retain the reviewed draft and exact request ID for retry.

Immutable revision updates/deletes are denied while their account exists; account deletion cascades all heads, revisions and request receipts. Privacy exports include all revisions, including removed connections. No financial value is calculated or modified. No background job, provider request or private-data automation is needed: all transitions are user-triggered.

The on-device handler uses the same contracts/domain checks, serialized local storage, owned records and actual dated content bundle. Bundle age remains visible. A rebuilt public bundle may change editions; loading computes review status without rewriting saved receipts. Device deletion removes the account's records. Local requests use the installed fetch bridge and cause zero external API requests.
