# Research policy and threat model — DEV-002

This document describes the implemented application and its explicit boundaries. It completes a design deliverable, not a security certification, production approval or test pass. Source code, feature specifications and current verification in development/status take precedence over historical blueprint claims. Recent source-recovery/read-admission changes may be authored but unverified; their controls are not represented as passing runtime tests.

## Assets and trust boundaries

Protect account credentials/sessions/recovery codes, owned financial inputs and histories, private notes, feedback attachments, operator credentials, source evidence and immutable published/issued records. Browser input, spreadsheets, source XML/HTML, provider output and quoted text are untrusted data. They cannot authorize actions, invoke tools, select arbitrary provider destinations or override account ownership. PostgreSQL holds structured records and ownership; MongoDB holds source evidence. These stores do not share an atomic transaction. The connected API is separate from device-only storage and from an operator session.

## Allowed vocabulary and activation gates

Use **recorded**, **reported**, **source says**, **captured at**, **user-entered**, **hypothetical**, **contribution-only**, **review needed**, **unavailable**, and **historical receipt** according to their actual provenance. An observation is not an expectation; a scenario is not a forecast; a user's research connection is not a verified causal edge. “No review trigger” in the fictional lab is not a hold recommendation or a statement of safety. Stale, conflicting or missing required inputs must not produce confident action language.

Do not label acquisition cost as market value or performance. Do not describe a saved goal gap as probability of success, suitability or guaranteed return. Source review approves a stored edition for its bounded reading scope, not investment advice or universal reuse rights. An operator's requested action is distinct from its completed receipt.

Personalised regulated advice, trade execution, recommended sizing and automatic portfolio action remain disabled. Activation needs its separate approved operating model, suitability/risk policy, validated inputs, costs/taxes, no-action comparator and reconstructable evaluated policy. These gates do not prevent completion of this documentation task or already specified educational/record-keeping features. They do prevent inventing absent advice behavior merely to close a roadmap row.

## Educational versus real-data objective

`educational-demo-v1` and `fixture-v1` use fictional instruments, prices and mechanisms. They demonstrate exact calculation, immutable review and stale/conflict refusal. They do not implement the accepted real evidence→factor→sector→company→holding→goal objective, which remains a runtime/source task. Existing real research connections store the user's chosen reason without asserting that chain as fact.

## Private storage implementation update — 2026-09-15

Authenticated AES-GCM envelopes are authored for customer identity, financial source revisions and previews, goal derivatives, allocations, reports/jobs/schedules, connections/reviews/impact, bond comparisons, private AI history, feedback and anonymous virtual financial records. Username lookup uses a separate stable HMAC key; payload-key rotation retains that lookup key. See [domain inventory](../development/private-domain-inventory.md) for exact migrations, legacy conversion and retention limits. Unknown/wrong-owner envelopes fail closed; deletion/recovery paths preserve their documented key-independent boundaries. This is authored implementation, not a passed security audit or a claim that historical database/backups were converted.

Minimum reading activity, public-reference preferences and consent/worker admission metadata deliberately remain queryable under owner access, purpose consent, export and deletion controls. Macro alert thresholds are public-indicator percentage points, not invested financial amounts. No arbitrary note/wealth/profile field is present in those schemas. Adding one requires the same sensitive-payload envelope boundary. A broker token vault is not applicable to the supported file import workflow: no broker OAuth/API credentials are accepted or persisted. A future connected broker integration must implement a vault before activation. Device-only storage uses the existing app/browser sandbox and owner isolation; this server envelope implementation does not assert an additional offline hardware-backed vault. Physical device, OS storage and deployment backup acceptance remain separate.

DEV028 follow-on: the disabled-by-default Zerodha connector now includes purpose-bound encrypted access-token/capture storage and owner-bound explicit callback completion, including a constrained Android handback. This supersedes the earlier vault N/A statement for Kite only. Normal provider tokens may have trading privileges; this app implements only session exchange/revocation and GET holdings. Live activation still requires registered app and applicable retention/deployment permission.
