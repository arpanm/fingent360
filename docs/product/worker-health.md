# Worker health and reviewed controls — WORKER-HEALTH-001

Operators need to distinguish an idle queue, a paused worker, an old observation and unavailable storage. Operations → Worker health reads aggregate server observations for saved-report preparation (including schedule materialization) and in-app reading reminders. It never displays user identities, job IDs, report labels/snapshots, reminder titles, source contents or raw exceptions. No provider, financial-record mutation, arbitrary retry or monitoring infrastructure is introduced.

The API supplies server observed-at, control version, paused state, last heartbeat, last successful completion and safe last-failure category (storage or preparation), plus bounded queue/due/active-lease/expired-lease counts and oldest outstanding age in seconds. Counts cap at10,000 with explicit more-available. Heartbeat freshness is fresh through30seconds, stale afterward, and not-observed before the first recorded poll. Fresh means a process recently reached the shared database; it does not assert every process is alive or that queued work succeeded. Database/API failure returns503 and the UI labels retained dated data historical/unavailable. Reminders use atomic row-locked batches, so leased counters are not applicable. No periodic browser refresh is required; explicit Reload observes the present state.

Pause/resume requires an operations session, expected control version, unique request ID and explicit confirmation. The receipt records only worker/action/version/server time. Replay of a retained request returns the immutable receipt, never an assertion of the current mode; the UI fetches current health afterward. A failed follow-up read preserves the receipt and disables controls until Reload succeeds. Conflicting expected versions return409 with Reload. Keep the latest1,000 control receipts per worker; prune only older control metadata during a new successful transition. After eviction an old expected version still conflicts, so a delayed old request cannot apply its former action. The UI discloses this bound. State versions increase monotonically; no-op transitions conflict. No private account deletion changes these aggregate, content-free controls/audits.

All report claims, scheduled-report materializations and reminder batches take a shared transaction lock on their fixed worker-control row before touching work. Pause/resume locks that same row exclusively and reauthorizes after waits using current server time. A committed pause fences all future admissions across processes. Already committed report claims can finish under their original lease, which is rechecked with wall-clock time after the finish row lock; the pause does not cancel them. Atomic reminder/schedule transactions admitted before pause finish before its exclusive lock can commit. Resume and restart retain existing job uniqueness, original snapshots, notification uniqueness, retry counts and lease semantics. Missing control schema fails closed. No cleanup, provider refresh or new job is performed by viewing health or changing control mode.

Migration030 adds two fixed control rows, two bounded observation rows and the bounded immutable control-receipt ledger. This feature is independently usable with migration030 and no scheduling module. A fixed current-schema relation check exposes dueSchedules:null and “Report scheduling is not enabled” when migration029 is absent. Once schedules are installed, dueSchedules counts real active due schedules separately from issuance. The schedule feature owns migration029 and calls the shared transaction admission helper. Actual work success is recorded alongside completion; failed transactions record a safe storage category only if the database subsequently permits it. A complete database outage cannot record its own failure, so stale/unavailable distinctions remain explicit.

Acceptance covers strict contracts and counts, guest/Origin rejection, session expiry/revocation after a control-lock wait, same-request replay and conflicts, rollback of audit/control, cross-instance claim fencing, already-claimed completion, expired-lease recovery, reminder uniqueness, restart persistence, bounded audit eviction, initial/read failures and Retry, lost control acknowledgement with historical receipt,401 clearing including late reads, confirmation/cancel/Back, keyboard focus/mobile layout. Offline Operations explains that worker controls apply to connected server work only; attempted local endpoints return503 with no API traffic or local financial changes. Exact cases and parent-run steps are in the development handoff. Authored acceptance is not executed verification.
